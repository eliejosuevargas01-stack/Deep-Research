## Decisões e adendo preciso ao roadmap

1. **Prefixo:** canônico `/briefings`, sem alias `/api/briefings`. O router legado `/api` não é requisito; `app/main.py` inclui router novo diretamente. Sem rotas duplicadas.
2. **POST síncrono:** validar request antes de settings-runtime/SERP/LLM e antes de criar/mutar briefing (autenticação/DB própria do auth é legítima e pode rodar antes do body handler); usar `orchestrate_persisted_briefing` uma vez e devolver snapshot final `draft` ou `failed`. Sem background task, scheduler, pesquisa legada ou fila. Chamar composição de dependências por request, não singleton de segredo em import. `JinaSerpClient` recebe chave runtime lida de settings numa sessão curta, fecha sessão antes da busca; instancia-se por operação (lock local não promete serialização global). `make_scout_complete(AsyncSessionLocal, default_timeout_s=30.0)` também pode ser construído por request; não invocar LLM legado `complete()` com retries internos. Timeout Jina/LLM deve ser finito, positivo e configurável por tentativa, default 30s, sem teto novo. Serviço usa mesmo valor configurado no outer LLM e binding `default_timeout_s`; não impor deadline global que corte retries ou Tx2. Até quatro tentativas totais por operação; SERP reaproveitado; binding envia `num_retries=0` e `max_retries=0`. Não criar retry externo/nested. Em cada operação, loop LLM sequencial; nenhuma promessa cross-process.
3. **Falhas e exposição:** prompt indisponível persiste `FAILED`, HTTP 500 com detalhe público fixo; SERP esgotada ou LLM esgotado persiste `FAILED`, HTTP 503 com detalhe fixo. A factory `make_scout_complete` valida timeout, mas resolve settings/modelo/chave somente quando callable é invocado após Tx1 e SERP; retirar promessa de validação LLM pré-Tx1. `ProviderConfigurationError` descoberto nessa invocação não entra em retry/`LLMAttemptError`; wrapper após Tx1 tenta emergência `FAILED` com `Processamento abortado ou cancelado`, repropaga a mesma exceção e a fronteira HTTP retorna 500 genérico fixo. Isto é tentativa best-effort, não garantia de persistência em crash/falha DB. Configuração/chave Jina inválida (`ValueError` somente ao construir/verificar Jina, antes de Tx1 após tema válido e auth) retorna 500 genérico sem briefing. `app/briefing/service.py:182–194` permanece inalterado; `CancelledError` repropaga e não vira resposta normal. Unknown sem retry/`LLMAttemptError`; wrapper tenta emergência após Tx1 e repropaga; default HTTP 500 seguro. Upstream auth: mapear classes concretas `litellm.exceptions.AuthenticationError` e `litellm.exceptions.PermissionDeniedError`; também `litellm.exceptions.APIError` cujo `status_code`, ou `httpx.HTTPStatusError` cujo `response.status_code`, seja inteiro não-bool 401/403 → HTTP 500 genérico fixo. Não classificar por atributo/texto/string em exceção arbitrária. Capturar `ValueError` apenas na construção/verificação Jina, nunca no handler inteiro. Falha CAS `BriefingVersionConflictError` → 409; `InvalidTransition`/estado incompatível → 409; `InvalidContent`/schema tema ou pontos → 422; inexistente → 404. Nenhuma resposta pública inclui strings dinâmicas, chave, prompt integral, payload provedor ou traceback. Não alterar service/binding.
4. **Auth e transação:** reutilizar `Depends(require_admin)`; nada de auth nova. Bearer/API-key já retornam sem SELECT; cookie faz SELECT em `AdminSession`, abrindo autobegin via `get_db`. Mesma instância `get_db` e ordem de dependências FastAPI são inequívocas: rota declara `db: AsyncSession = Depends(get_db)` e `principal = Depends(require_admin)`, auth conclui antes do corpo da rota. Depois de auth/CSRF e antes de operação/rede, rota chama `db.rollback()` somente se `db.in_transaction()`, encerrando somente a transação de leitura da sessão de request, sem `commit`. Rollback pode expirar/destacar ORM `Principal`: a feature não lê atributos de `Principal` após o rollback, usando apenas o fato de autorização concluída (escalares, se algum dia necessários, exigem snapshot antes do rollback — não é o caso desta feature). Não alterar `security.py`; não usar sessão caller-owned do binding; sessão request permanece propriedade da camada HTTP. GET segue a mesma regra: liberar transação após autenticação, antes da query de domínio. Testes devem executar `require_admin` verdadeiro contra SQLite isolado para sem credencial 401, CSRF ausente/incorreto 403 e sucesso de cookie; bearer/API-key válidos preservados. Sem permissive override como prova exclusiva. Nunca afirmar que 422 de validação prevalece sobre 401/403 para request não autenticado — autenticação/DB próprio do auth é legítima e pode rodar antes do body handler.
5. **Request shapes:** create `BriefingCreateRequest`; patch `BriefingEditPointsRequest`; approve/reopen aceitam corpo omitido, JSON `null` explícito ou objeto vazio `{}` como no-op. Array `[]`, string, número, boolean e objeto com extras → 422 (`extra="forbid"`). Rejeições preservam snapshot corrente e histórico. Testes futuros cobrem omitido/null/{}/[]/string/number/bool/extra e comparam snapshot+history nos rejeitados. Não aceitar campos de mutação alternativos.
6. **D4 bloqueante:** `BriefingResponse` hoje não possui `version/error/approved_at`; `BriefingVersionResponse` inexiste. `audit/t011-integration-decomposition.md:57–77` exige os campos/schemas, mas ações não possuem recorte de schema/tests. Adicionar pré-requisito mínimo e explícito antes de router: `app/briefing/schemas.py` — `BriefingResponse.version: int = Field(default=1, ge=1)`, `error: str | None = None`, `approved_at: datetime | None = None`; novo `BriefingVersionResponse(version>=1,status,points default [],error=None,approved_at=None,created_at: datetime)`, `extra="forbid"`; manter validação 3–7 para draft/approved. Novos testes dedicados `tests/test_briefing_schemas.py` cobrem validação/serialização e extra forbid, sem router. Parent deve inserir esta ação prévia e sua dependência em T025/T026 no `actions.md`; T025/T026 não coding até auditoria aceitar ajuste. Não criar schema inline no router. `ApprovedBriefingResponse` atual já cobre publicação.

## Matriz endpoint → símbolos → teste HTTP

Todos os testes em `tests/test_briefing_api.py`, FastAPI `TestClient`/`httpx.AsyncClient` com `ASGITransport`, SQLite temporário isolado e app importada sem executar lifespan legado; dependency override apenas para DB/session factory e dependências de I/O, nunca para remover auth nos testes de auth. Sem rede, DB real, `.env` ou chamadas LiteLLM/Jina reais. Registrar router em `app/main.py`; criar app import não deve disparar lifecycle de scheduler legado.

| Critério / rota | Contrato / símbolo real | Verificação HTTP observável |
|---|---|---|
| `POST /briefings` sucesso | `BriefingCreateRequest`; `orchestrate_persisted_briefing`; response `BriefingResponse`; 201 | theme válido, fake SERP/LLM, ID UUID gerado no domínio, status draft/version final, uma invocação, sem scheduler; verificar registro corrente e snapshots históricos coerentes. |
| POST conteúdo inválido | Pydantic + `validate_theme` | 422 antes de qualquer leitura de settings-runtime, SERP ou LLM e sem criação/mutação de briefing; autenticação pode legitimamente consultar DB via `get_db` antes do body handler. Sem briefing criado. |
| POST prompt falha / SERP falha / LLM esgotado | `PromptUnavailable`, `SerpSearchError`, `LLMAttemptError` encapsulados pelo serviço em FAILED | respectivamente 500 fixo e 503 fixo; estado FAILED persistido e versão histórica; assert resposta não inclui sentinelas de segredo/erro. |
| GET `/briefings/{id}` | `get_briefing` + `BriefingResponse` | draft/failed/approved expõem versão, status, pontos; ausência 404; nenhum campo extra. |
| PATCH `/briefings/{id}` | `edit_briefing`, `save_briefing_transition`, `BriefingEditPointsRequest` | versão +1 e history append; aprovado/estado incompatível 409; pontos 2/8/vazios 422 sem alteração de DB/histórico; CAS 409. |
| POST `/briefings/{id}/approve` | `approve_briefing(now())`, CAS; `BriefingApproveRequest` | body omitido, `null` ou `{}` no-op; `[]`/string/número/bool/objeto com extra 422; sucesso 200 e versão +1/approved_at; pontos inválidos 422 sem mutação; estado errado 409; ausente 404; rejeições preservam snapshot+history. |
| POST `/briefings/{id}/reopen` | `reopen_briefing`, CAS; `BriefingReopenRequest` | mesmas regras de body; aprovado→draft, +1 e approved_at null; estado errado 409; ausente 404. |
| GET `/briefings/approved/{id}` | `read_approved`, `ApprovedBriefingResponse` | aprovado 200 read-only; SELECT DB permitido, zero I/O externo/SERP/LLM/pesquisa; existente não aprovado 409; ausente 404; verificar contagem de versões inalterada. |
| GET `/briefings/{id}/versions` | `get_briefing_versions` + `BriefingVersionResponse` | lista ASC somente snapshots de transição v2+; `generating` corrente v1 não é histórico consultável; pai inexistente 404 (não lista vazia); response inclui `created_at`, sem `briefing_id`/campos extras. |
| Auth/CSRF | `require_admin` real | sem credencial 401; cookie mutation sem CSRF/CSRF inválido 403; credenciais bearer/API-key e cookie+CSRF bem-sucedidos; sessão auth sem transação aberta durante fake SERP/LLM. |

Versionamento: cada transição aceita incrementa uma unidade e appenda snapshot em transação atômica; request rejeitado não altera current nem history. Tx1 persiste somente `BriefingRecord` corrente em `generating` v1; não insere `BriefingVersion`. Histórico append-only começa na primeira transição v2+, listada em ordem ASC; não criar insert v1 nem migration para isso. Erro de configuração LLM (ProviderConfigurationError) descoberto na invocação do callable após Tx1/SERP não é convertido em retry ou LLMAttemptError; o wrapper tenta emergência FAILED com a mensagem fixa Processamento abortado ou cancelado (best-effort, sem garantia de persistência em falha de DB ou crash), repropaga a mesma exceção e a fronteira HTTP a traduz em 500 genérico seguro conforme item 3.
